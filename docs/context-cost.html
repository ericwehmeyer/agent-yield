What we found

Where it goes

1. Half of all main-session calls carry more than 236,360 tokens. A call reads its whole context before it does anything. At that size it bills a quarter of a million tokens to run a two-line command.

2. Subagents cost three times what they need to. The median subagent call carries 96,583 tokens. One given a written brief and told not to explore carries 31,618. The difference is the agent reading the repo to work out what you meant.

3. Nothing warns you, because nothing happens. Cost does not jump at a threshold. It climbs from the first call to the last. We looked for a knee in the curve. There is none.

Our rules watch how full the window is. The window is never full. This session is using 15% of it and costs 154,559 tokens a call.

The shape of it

Main sessions and subagents need different limits

We have one set for both. The median main call carries 2.6 times the median subagent call. A subagent that grows past its brief is a briefing problem; a main session that grows is a restart problem. One number, and it is wrong for one of them.

So what

451 million tokens, and what to take off it

That is what went above the limits in the table below: 15% of everything. It is the gross figure. Restarting is not free, because a fresh session reads whatever you hand it. The last method change we measured end to end returned 1.07× where per-call arithmetic promised 6.2×. The parent session ate the difference.

So halve it. It is still 225 million tokens.

How do you know where you are? Run agent-yield status. It reads the live transcript and prints what this session is costing per call.

A moment ago it called this session cheap at 154,559 tokens a call, because 154,559 is 15% of a million-token window. It was right by accident. The next section is about the accident.

What changed after this page

The limits were percentages. They are token counts now, and that cost us half the saving.

The code stored them as fractions of the window: COST_KNEE = 0.20. The idea was that a fraction survives a change of model.

It does not. A call carrying 200,000 tokens costs 200,000 tokens. Change the window to two million and the same call is cheap; change it to half a million and it is steep. The bill never moved. The window has nothing to do with the price. How full the window is, and what a call costs, are different questions, and writing both as percentages is what hid this for a month.

Fixed the same night, in #23, on two machines at once. The limits are absolute tokens and the cost path no longer takes a window at all.

Setting the actual numbers was the harder half, and it was not free. The first proposal was 150,000 / 250,000 / 400,000, and 250,000 is this machine's median main-thread call: a restart rule that fires on every second call. A rule that fires that often gets turned off, and a rule that is turned off saves nothing. So the numbers moved up, to 300,000 / 500,000 / 700,000.

That is the whole trade, and there is no way around it. Leverage climbs as the limit rises. The share of spending caught, divided by the share of calls disturbed, goes 1.25, 1.49, 1.60, 1.87, 2.24, 2.67. It never climbs faster than coverage falls away. There is no knee to hide in. Moving the restart line from 250,000 to 500,000 took the estimate on this page from 565 million tokens to 451 million, and most of what survives now comes from the gentlest rule of the four.

All figures from .agent-yield/calls.jsonl: 20,757 calls, deduplicated, 2026-08-26. Context per call is cache_read + input + cache_creation. The medians and the spend figures are measured. The limits (300,000, 500,000, 700,000 for a main session, 150,000 for a subagent) are chosen, not discovered: the curve has no break in it. Each is recorded in thresholds.py with the share of calls it fires on. One operator, one machine; issue #20 is a blind re-run on a second.
