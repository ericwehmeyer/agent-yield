Every threshold we have measures the wrong thing

The rules in design.md §5 fire when the context window gets full. Nothing fires when a call gets expensive. On a 1M window those are nearly 600,000 tokens apart — and almost all the money is spent in the gap.

The argument

A full window and an expensive call are not the same event

§5 has one family of thresholds and they are all percentages: warn at 60% of the window, compact at 75%, compact now at 85%. That is the right shape for the question am I about to run out of room. Room is a fraction of a window, so a percentage is the honest unit.

But cost is not a fraction of anything. A call carrying 200,000 tokens costs 200,000 tokens whether the window is 200K or 1M. The window does not appear in the bill. So a cost threshold has to be an absolute number of tokens, and none of ours are.

The consequence is the picture below.

Last night this session stopped at 212,000 tokens believing it had become bloated. It was at 21% of the window — silent under every rule in §5, and the concession looked like an overreaction.

It was not an overreaction. 212,000 is below the median main-thread call. The instinct was right and no instrument agreed with it.

Finding one

Main threads and subagents are two different populations

§5 has a single threshold family applied to everything. But the two roles do not live in the same range at all — the median main call carries 2.6× the context of the median subagent call. One number cannot serve both, and today the same number serves both.

Finding two

There is no knee, and the 200K edge was an artifact

The measurement that opened #17 said 47% of the bill comes from calls above 200K. That number is real. But 200,000 was a bucket edge chosen to print a histogram, not a break discovered in the data.

Plotted continuously, the main-thread curve just decays. 83% → 74% → 65% → 42% → 21%, smooth the whole way. There is no natural threshold in here to find.

That is a negative result and it matters: it means #17 cannot be solved by looking harder at the data. Any threshold we set is a policy choice, and the honest version says so instead of dressing a chosen number as a discovered one.

Finding three

The missing knee has a cause, measured independently

While this page was being drawn, the second machine fitted the cost of a unit of work against its length and found it superlinear: briefed agents at calls1.54, the parent session at calls1.41. Context grows with every call inside a unit, so each call re-reads a bigger pile than the last.

That explains Figure 3. There is no knee because nothing discrete happens — a session does not cross into an expensive state, it accumulates into one, continuously, from its first call. A smooth curve is the signature of a smooth process, and the two machines measured the two halves of the same fact without coordinating.

It also relocates the lever. If cost is superlinear in unit length, the saving is in shorter units, not fewer: the same 27 calls run as three 9-call agents cost 840,036 against a measured 1,879,466 for one 27-call agent — 2.2×, for identical work.

And a caution on the 7.9× above. That ratio is real per call. End to end it mostly disappears: the same machine measured the whole method at 1.07× per issue against per-call economics predicting 6.2×, because the parent ate the gain reading every diff itself. Per-call economics is a true statement about calls and a poor prediction of a session.

The proposal

A second family, in tokens, that never mentions the window

Capacity thresholds stay exactly as they are — percentages, because capacity genuinely is a fraction of a window. Cost thresholds get added beside them as absolute token counts, per role, because tokens are absolute.

The one measured quantity available to anchor against is the briefed-agent floor of 31,618. The multiples below are derived from it. The round token numbers are chosen.

Open disagreement with the code as shipped. #17 was closed on the other machine while this page was being drawn, with the cost family implemented as fractions of the window — COST_KNEE = 0.20, COST_STEEP = 0.40 — reasoning that fractions survive a model change.

They survive it syntactically and break it semantically. Cost is context × rate; the window W does not appear. Writing the threshold as 0.20 × W makes it move when the window changes, so the same 200,000-token call is cheap on a 2M window and steep on a 500K one, while costing exactly the same in both. The measured quantity was 200,000 tokens; the 0.20 is an artifact of dividing by a number that plays no part in the bill. The code's own comment concedes it — "calibrated on a 1M window only; on smaller windows it is conservative" — and a cost threshold should need no window caveat at all.

The advice is different, not just the number. Every capacity rule ends in compact. Every cost rule must end in dispatch or restart. Compacting an expensive session pays for a summarisation pass and then keeps paying, because the context you rebuilt is re-read on every call that follows.

Which of these numbers are measured, and which are chosen
